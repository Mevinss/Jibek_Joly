# Jibek Joly

Jibek Joly is an advisory hackathon railway dispatch demo for presenters, judges and people exploring dispatch decisions. It is not a train control or railway safety system. The own rail SVG and the name Jibek Joly are the only brand identity: no subtitle, organizer logo, organizer slogan or organizer photos are authorized.

The original dispatcher, preserved in this branch at `/dispatch-original.html`, is the FastAPI-served workspace, using the shared `services/ai/web/dispatch.css` and `dispatch.js`. Both `/` and `/frontend/` show this single page, so future dashboard panels can be added without a second copy of the interface or its API logic. Plain HTML/CSS/JavaScript, locally bundled i18next/MapLibre and local fonts require no Node build or runtime CDN. Light theme and Russian are defaults; a saved preference can select dark theme or Kazakh. RU and KK are the only requested interface languages. Kazakh translation review by a native speaker remains a separate quality requirement. The desktop-first workspace adapts to narrow screens; no dedicated mobile driver interface is in scope. Dispatcher and manager roles change presentation only, not permissions.

The working screen links map, timetable diagram, train register and one train/station drawer. The 28 visible SIM services run on the demonstration Көкшетау — Астана — Алматы corridor, entirely inside Kazakhstan. Source station coordinates and local Natural Earth country geometry support an offline vector map and a “Без WebGL” SVG mode. Connections, kilometer positions, movements, station track layouts and the uploaded timetable are approximate or synthetic, not operational ҚТЖ data. Short train labels retain SIM context and full identifiers remain in technical details.

A one-hertz SSE demonstration stream supports pause, ×1/×10 tempo, reset, incident injection, train following, recorded-history replay and CSV export. “Прямой эфир” means this demonstration stream. The diagram has timetable lines, recorded movement and current-speed extrapolation, with station/kilometer axes and zoom. It does not display an optimized dispatch plan. Source and precision notes, explicit units, UTC+5 and the advisory footer are part of the product. The map uses local geometry without external tiles. A stream failure freezes positions and reports reconnection; forecast and chat request failures must remain visible.

The movement index is a transparent demo formula from the simulated snapshot, with individual point deductions and a five-minute trend. It is not a certified or validated operating-quality metric. An incident can open a twenty-second two-train scheduling exercise: choose either train first or hold both, inspect calculated alternatives against FIFO, and record the selection or timeout default C. Its score, seed and comparison apply only to that exercise. They do not change the map timetable or movement index. Delay and energy proxy arithmetic in that exercise is not proof of operational savings. A separate main-screen panel adapts the exact visible demo clock and incident to the platform contract, shows true FIFO ordering and a validated CP-SAT block plan for the exercise pair, and reports the full 28-train planning status separately. The pair plan excludes the other trains and does not change playback. CP-SAT + ML buffer remains unavailable because Kazakhstan ML transfer is unvalidated. The integration contract is in `docs/SOLVER_CONTRACT.md`. Station occupancy is current synthetic state; release times and occupancy twenty minutes ahead are not calculated.

Actual model inference remains separate from the visual simulation and the exercise. The PKP delay models were trained on Polish passenger journeys. Their transfer to Kazakhstan has not been validated, so the Kazakhstan advisory view suppresses untrusted delay/risk numbers and explains that boundary. It can show current delay, known incident wait and an explicitly demo restriction component. It never invents a reliable ML addition or a calibrated Kazakhstan interval. Unsupported train types use `rule_fallback`, a heuristic rather than ML. OOD inputs must be identified as unreliable. The current delay-growth probability means growth of at least three minutes on the next block; the legacy `p_conflict_15m` contract field remains a next-segment proxy and is not a validated fifteen-minute conflict probability.

The integrated ML Laboratory loads reproducible PKP baseline errors, calibration, test-run replay, model-card and feature evidence. SHAP describes the original classifier's log-odds before calibration, not causality or percentage-point probability effects. The separate `kz-synthetic-schedule-v1` model learns scheduled segment duration, not delay. Its familiar-segment test and held-segment failures are evidence about synthetic schedules only; its MAE must never be sold as accuracy on real Kazakhstan journeys. The displayed physical travel-time formula and grouped residual experiment are demonstrations, not validated arrival forecasts. Existing model endpoints and the older Russian workbench at `lab.html` remain available; that legacy page retains its earlier green/Golos presentation and is not the new visual-system authority.

The assistant uses the snapshot captured at submission; it must not substitute fixture state or unrelated solver results. Russian chat can use the server-side provider or its fallback; Kazakh currently returns a constrained local summary of the selected snapshot rather than a full Kazakh LLM conversation. API keys and OpenAI calls stay server-side. Delay/reserve experiments pause playback and request actual inference without rewriting the timetable.

Success means a presenter can follow one SIM train, explain an incident and known wait, distinguish measured/model/demo quantities, inspect honest model evidence and understand unavailable capabilities. The current source contains the review correction batch for forecast failures, score wording, map collisions, narrow diagram scrolling, UTC+5, dynamic language state and laboratory theme changes. The integration panel has been checked in a local browser at 1366 and 600 px; a full post-integration visual matrix and performance acceptance remain pending. No 60 fps guarantee or sub-500 ms update guarantee is claimed. Current integration checks and limits are in `docs/UNIFIED_INTERFACE_STATUS.md`; the prior visual review is in `docs/design/VALIDATION.md`.

Run with Python 3.11: install `services/ai/requirements.txt`, then `python -m services.ai.main` from the repository root. Follow repository tests and schema-export instructions when changing backend behavior or contracts. Product and design context do not mandate a particular skill or plugin.

It preserves the team reference map, city/station tabs, Three.js station, arrival board, four A/B scenarios, dispatcher game, dashboard and causes. The reference map/game and backend snapshot remain independent; game choices and pair plans do not control playback.
